mTLS for browser clients connecting to the tunnel

Design discussion — captures the questions raised, the choices made, and the proposed v1 surface for adding mutual-TLS authentication to the public listener of swe-swe-tunneld.

Goal

Let an operator gate the public, browser-facing HTTPS port of a swe-swe-tunneld instance with mutual TLS, so only browsers presenting a client certificate signed by a trusted CA can reach the tunnelled apps behind it.

Scope & non-goals

  • In scope: mTLS on the public browser-facing HTTPS listener; CA trust configuration; an ergonomic "mint your own CA" path for hobbyists; identity propagation to upstream apps.
  • Out of scope (v1): client-side CSR enrollment, OCSP/CRL revocation, per-host mTLS policy. The agent control plane keeps its existing Ed25519 pubkey allowlist — mTLS does not apply to it.

Decisions taken in this discussion

QuestionDecision
GranularityPer instance. The whole daemon is mTLS-only or it is not. Mixed deployments run two daemons.
Trust anchorSupport both — bring-your-own CA and a built-in "mint your own" subcommand.
Failure modeStrict TLS rejection (RequireAndVerifyClientCert); browser shows native error.
Identity propagationForward X-Client-CN and X-Client-Cert-Fingerprint headers to upstream after stripping any inbound copies.
Scope on portsPublic browser-facing listener only. Agent registration stays Ed25519-only.

Does the browser have to generate its own cert?

No — not in the v1 design. The CA, running inside swe-swe-tunneld, mints both the private key and the cert server-side, packages them as a passphrase-protected .p12 file, and the user imports that into their OS / browser keychain. The browser then presents it automatically on subsequent handshakes.

Alternative considered: the browser-side generates a private key locally and submits a CSR to the CA, so the private key never leaves the user's machine. More secure, but needs an enrollment portal. Deferred to a later iteration once an enterprise actually asks for it.

Sequence diagram — a) enrollment / cert issuance

sequenceDiagram autonumber actor Op as Operator participant D as swe-swe-tunneld participant Disk as Daemon FS (./mtls/) actor U as End user (Alice) participant B as Alice's browser / OS keychain Op->>D: swe-swe-tunneld mtls-init D->>D: generate CA key + self-signed CA cert D->>Disk: write ca.key (0600), ca.pem Op->>D: swe-swe-tunneld mtls-issue --cn alice D->>D: generate alice.key + sign alice.crt with ca.key D->>D: bundle into alice.p12 (passphrase-protected) D-->>Op: alice.p12 + passphrase Op-->>U: deliver alice.p12 + passphrase out-of-band U->>B: import alice.p12 into keychain B-->>U: cert now available for TLS client auth Op->>D: restart with --mtls-ca ./mtls/ca.pem D->>D: public listener now requires & verifies client certs

Sequence diagram — b) browser connects to a tunnelled app

sequenceDiagram autonumber actor U as Alice participant B as Browser participant D as swe-swe-tunneld (public :443) participant A as Agent / upstream app U->>B: open https://app.example.com B->>D: TLS ClientHello (SNI=app.example.com) D-->>B: ServerHello + server cert (LE) + CertificateRequest (CAs=[ca.pem]) B->>U: cert picker — choose a cert for app.example.com U->>B: select Alice's cert B->>D: Certificate(alice.crt) + CertificateVerify(signed with alice.key) D->>D: verify alice.crt chain against ClientCAs pool alt cert valid D-->>B: Finished — handshake complete B->>D: HTTPS GET / D->>D: strip inbound X-Client-* headers D->>A: GET / + X-Client-CN: alice + X-Client-Cert-Fingerprint: sha256:… A-->>D: 200 OK D-->>B: 200 OK else cert missing or bad D--xB: TLS alert (bad_certificate) — connection closed B->>U: native "your connection isn't private" error end
Things worth calling out:
  • The cert-picker dialog in step 4 of diagram (b) is browser-native — we don't control its look. First-time users sometimes find it confusing; most browsers remember the choice per origin after the first selection.
  • The CA cert (ca.pem) does not need to be installed in the browser's trust store — only the daemon's ClientCAs pool needs to trust it. The browser only needs the .p12 for its identity.

Proposed config surface

FlagEffect
--mtls-ca <path>When set, enables mTLS on the public listener and loads the PEM bundle as the trusted client-CA pool.
--mtls-ca-dir <path>
(default ./mtls/)		Where the self-mint mode reads / writes the CA key + cert.

Subcommands (ease-of-use mode)

SubcommandEffect
swe-swe-tunneld mtls-initGenerate a self-signed CA into --mtls-ca-dir. Operator then points --mtls-ca at the resulting ca.pem.
swe-swe-tunneld mtls-issue --cn <name> [--days N]Sign a client cert + key against the local CA and write out a <name>.p12 bundle.

Runtime behaviour

  • tls.Config.ClientAuth = RequireAndVerifyClientCert on the public listener.
  • ClientCAs populated from the file passed to --mtls-ca.
  • Bad or missing client cert → TLS handshake fails, browser shows its native error. No friendly 403.
  • On each accepted, proxied request, the handler:
    1. strips any inbound X-Client-* headers (anti-spoof);
    2. reads the verified peer cert from r.TLS.PeerCertificates[0];
    3. sets X-Client-CN = subject CN, X-Client-Cert-Fingerprint = SHA-256 of the DER.

Tests planned

  • Unit: cert chain validation, header stripping / injection, p12 round-trip, CA mint.
  • E2E: real TLS handshake with valid cert (200), missing cert (handshake fails), wrong-CA cert (handshake fails), header forwarding to a stub upstream.

Open follow-ups: CSR-based enrollment, revocation (CRL or OCSP), browser UX for self-signed CA edge cases. None blocking for v1.
